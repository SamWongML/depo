A terminal multiplexer written in 2007 for sysadmins turned out to have exactly the four properties agent orchestration needs in 2026: per-pane PTY isolation, server-side session persistence, real-time visibility into many processes at once, and a stable textual API (send-keys, capture-pane, pipe-pane).

Nobody designed it for this. That is why it works: every agent CLI is just a foreground process in a pty, and tmux is the most boring, most scriptable, most already-installed way to own a pty.

The productivity gains are not in tmux itself. They come from three things it enables: isolation (agents that cannot corrupt each other's working tree), attention routing (you find out an agent is blocked in seconds, not in 40 minutes), and addressability (a stable name like main:3.1 that both you and the agent can talk about). This manual is organised around those three.

The client–server split is the whole trick

Running tmux does not start a terminal. It starts a server that owns your sessions, and connects your terminal to it as a client over a Unix socket. Close the laptop, drop the VPN, get on a plane — the client dies, the server does not. Every agent mid-refactor keeps going.

  your laptop            the box (local or VPS)
  ───────────            ──────────────────────────────────
  ┌───────────┐   unix   ┌──────────────────────────────┐
  │ terminal  │◄─socket─►│  tmux server (detached-safe) │
  │  client A │          │                              │
  └───────────┘          │  session "api"               │
                         │   ├── window 1 ── pane %0 ───┼──► pty ─► opencode
  ┌───────────┐          │   │             └ pane %1 ───┼──► pty ─► npm run dev
  │  phone    │◄─ssh────►│   └── window 2 ── pane %2 ───┼──► pty ─► pi
  │  client B │          │                              │
  └───────────┘          │  session "infra"  ...        │
                         └──────────────────────────────┘
  clients are views.       processes live here and outlive every view.
Fig 1. Each pane owns a distinct kernel pty, so two agents writing at once never interleave into one buffer, and Ctrl-C to one pane cannot touch another.

Four properties, four consequences

The release cadence tells the story

tmux went 14 months between 3.5 and 3.6, then shipped 3.7 seven months later. Several of the recent additions land squarely on agent workflows: extended-keys handling that lets TUIs distinguish Shift+Enter, passthrough for escape sequences that carry notifications, and in 3.7 a floating-pane primitive and OSC 9;4 progress forwarding.

What tmux does not give you

It is not a sandbox. PTY isolation is process-level plumbing, not a security boundary: panes share your filesystem, your network namespace, your credentials, your SSH agent. An agent that runs rm -rf in a pane deletes your real files. Section 10 covers what to layer underneath.

It is also not an event system. tmux emits text on a screen, not JSON on a bus. Every orchestrator built on top pays a screen-scraping tax, and every one of them has re-paid it. Prefer real hooks from the agent (Section 05) over pattern-matching pane output whenever the agent offers them.

Restart, don't reload, after upgrading

tmux is a server. A new binary does not take effect in running sessions — tmux kill-server and start fresh. The 3.6 and 3.7 release notes both call this out; skipping it produces confusing "not a terminal" errors on attach.

Keybinding collisions: the map nobody draws

Every TUI agent claims Ctrl-chords, and so does tmux. The failure mode is silent — you press the key, tmux eats it, the agent never hears it, and you conclude the agent is broken.

  keystroke ──► terminal emulator ──► tmux ──► agent TUI
                       │                │            │
        Cmd/Super combos│      prefix +  │  leader +  │
        must be         │      bindings  │  chords    │
        translated here │      eaten here│            │
                        ▼                ▼            ▼
                   Alacritty/       C-b (default)  opencode: C-x
                   Ghostty/         C-a, C-f, C-w  claude:   C-o, C-t
                   WezTerm cfg      (your choice)  pi:       C-l, C-j
Fig 3. Three layers compete for the same chords. Pick a tmux prefix none of your agents use (C-f and C-w are popular precisely because agents rarely bind them), and add explicit send-keys passthroughs for the two or three agent chords you actually need.

Per-agent notes

  • Pi documents extended-keys on + extended-keys-format csi-u as the recommended setup, and binds Ctrl+J as a newline alias so Shift+Enter still works through terminal remaps. It requires tmux 3.5+ for the csi-u format; on 3.2–3.4 omit the format line and Pi falls back to xterm modifyOtherKeys.
  • Claude Code wants allow-passthrough, extended-keys and the extkeys terminal feature. If you use its fullscreen renderer, avoid iTerm2's tmux -CC control mode — it breaks the alternate screen buffer and mouse tracking. Plain tmux inside iTerm2 is fine.
  • opencode uses Ctrl+X as its leader, which avoids most tmux prefixes out of the box. Its common tmux complaints are Escape latency (escape-time) and clipboard on WSL2 (set-clipboard on plus allow-passthrough on).
  • Mouse mode is genuinely contested. Turn it on if you use a fullscreen agent renderer and want wheel scrolling inside it; turn it off if you prefer native terminal text selection. There is no universally right answer, only a decision you should make once.

┌─03Topology: mapping work onto panes

Sessions, windows and panes are cheap. The scarce resource is your attention. Choose the shape that puts exactly one decision in front of you at a time.

Three topologies dominate real setups. They are not mutually exclusive — most people run A as the frame, B inside a window when they are actively supervising, and C when they fan out.

A · Session per project, window per task

Addressing: the convention that pays for itself

tmux targets are stable strings: session:window.pane. Once you commit to one session for most work, main:3.1 unambiguously means window 3, pane 1. That string is useful to you — and it is far more useful to the agent.

Write the convention into AGENTS.md / CLAUDE.md and the agent can act on it directly: read the backend log in another pane, re-run a command from a pane's history, check whether the dev server recovered. This is the cheapest capability upgrade available, and it costs one paragraph of prose.

AGENTS.mdexcerpt
## Terminal layout

I work in a single tmux session named `main`. Panes are addressed as
`main:<window>.<pane>`. When I say "tmux 3.1" I mean `main:3.1`.

- `main:2.0` — API server, live reload, always running
- `main:2.1` — worker queue
- `main:5.0` — psql attached to the dev database

You may read any pane with `tmux capture-pane -p -t main:2.0 -S -200`.
You may send commands with `tmux send-keys -t main:5.0 ... Enter`.
Do NOT send keys to a pane that is running another coding agent.
Do NOT run `kill-session` or `kill-server`.

For a command that takes longer than ~30s, run it in `main:2.1` and
signal completion with `tmux wait-for -S build-done` rather than
blocking your own turn.

How many agents, actually?

The honest answer from practitioners and from Anthropic's own guidance converge: three to five. Token cost scales linearly with the number of independent contexts, while useful throughput saturates because coordination overhead, file conflicts and your review bandwidth all grow. Anthropic's documented rule of thumb is 3–5 teammates with roughly 5–6 tasks each, and never two agents editing the same file.

Rule of thumb

Add an agent only when you can name the file set it owns and nobody else touches. If you cannot draw that boundary, you do not have a parallel task — you have a sequential one you are hoping to shortcut.

┌─04Parallel agents and git worktrees

Agents sharing a working tree do not collaborate. They corrupt each other: half-written files become type errors in someone else's build, and every diff mixes three unrelated changes.

The fix is not clever coordination between agents. It is hard isolation at the filesystem level so no coordination is needed. git worktree gives each agent its own checked-out directory backed by the same .git, and tmux gives each directory a window. The pairing is the whole workflow.

the manual version~8 lines, no tooling
# create an isolated workspace for one task
git worktree add .worktrees/fix-auth -b fix-auth
cp .env .worktrees/fix-auth/.env            # copy, don't symlink
ln -s "$PWD/.turbo" .worktrees/fix-auth/.turbo   # share caches

# give it a window and start the agent there
tmux new-window -n fix-auth -c "$PWD/.worktrees/fix-auth"
tmux send-keys -t fix-auth 'opencode' Enter

# ... later, when the diff looks good
git merge fix-auth && git worktree remove .worktrees/fix-auth
tmux kill-window -t fix-auth && git branch -d fix-auth

What else needs isolating

A worktree isolates files. It does not isolate the rest of your dev environment, and two agents both running npm run dev on port 3000 will fight.

ResourceApproach
PortsDerive from worktree index or branch-name hash; put it in a per-worktree .env.local
DatabasesBranch the database, or one schema/container per worktree; never share a mutable dev DB across agents
Secrets / .envCopy, never symlink — a symlink means one agent's edit rewrites everyone's config
Build cachesSymlink (.turbo, node_modules/.cache, target/ where safe) — this is what makes worktrees cheap
DependenciesRun install once per worktree at creation, in a background pane, so the agent doesn't start on a broken tree

Worktrees are isolation, not security

A worktree stops agents from stepping on each other's files. It does nothing to stop an agent from writing outside the worktree, reading your SSH keys, or making network calls. Curated sandbox lists explicitly flag worktree+tmux tooling as useful alongside a real sandbox and not a boundary on its own. See Section 10.

┌─05Observability: the idle-agent tax

The single largest source of wasted time in multi-agent work is not bad output. It is an agent that hit a permission prompt four minutes in and sat silent for the next eighty-six.

Three states are enough

Independently built tools — tmux plugins, status-bar monitors, Rust multiplexers, GUI overlays — converged on the same tiny state machine. Adopt it, because everything downstream (colours, sounds, push notifications) hangs off it.

                    ┌───────────────────────────┐
     you prompt ───►│         WORKING           │◄──── you answer
                    └──┬────────────────────┬───┘         ▲
   permission request,│                     │ turn ends   │
   question, tool     │                     │             │
   approval           ▼                     ▼             │
            ┌──────────────────┐   ┌──────────────────┐   │
            │   NEEDS INPUT    │   │       DONE       │   │
            │  (blocking you)  │   │ (awaiting review)│   │
            └────────┬─────────┘   └────────┬─────────┘   │
                     └──────────────────────┴─────────────┘
                     cleared when you FOCUS the pane, not
                     when the event fires — otherwise the
                     signal flashes and vanishes unseen
Fig 8. working needs input done — the deferred reset is the detail that makes this usable. State clears on focus, using tmux focus-events.

Where the state comes from, per agent

Prefer real hooks over screen-scraping. Every major agent now emits something you can hang a script on; scraping the pane for a spinner glyph is the fallback, not the design.

#!/usr/bin/env bash   ~/bin/agent-state.sh
AGENT=$1; STATE=$2
PANE=${TMUX_PANE:?not inside tmux}
WIN=$(tmux display -p -t "$PANE" '#{session_name}:#{window_index}')

case "$STATE" in
  working)     BORDER=colour61 ; ICON="●" ;;
  needs-input) BORDER=colour214; ICON="◐" ;;
  done)        BORDER=colour34 ; ICON="✓" ;;
esac

tmux set -p -t "$PANE" pane-active-border-style "fg=$BORDER"
tmux rename-window -t "$WIN" "$ICON $(basename "$PWD")"

# escalate only when you are not looking at it
if [ "$(tmux display -p -t "$PANE" '#{pane_active}')" != 1 ] \
   && [ "$STATE" != working ]; then
  tmux display-message -d 4000 "$AGENT $STATE in $WIN"
  command -v terminal-notifier >/dev/null \
    && terminal-notifier -title "$AGENT" -message "$STATE · $WIN"
  # walking away? push it to your phone:
  # curl -s -d "$AGENT $STATE in $WIN" ntfy.sh/your-topic >/dev/null
fi

The fzf-popup trick

Bind display-popup -E to a fuzzy file picker that writes the selected path into the active pane. Every agent's built-in file autocomplete is worse than fzf, and pointing an agent at exact paths is one of the highest-leverage habits in agentic coding. Two lines of config replace a plugin ecosystem.

┌─06tmux as an API the agent can call

Three verbs cover almost every automation case, and their syntax has been stable for twenty years. This is the part that turns tmux from a nicer terminal into an orchestration substrate.

VerbWhat it doesThe gotcha that costs an hour
send-keysTypes into a target pane as if from a keyboard, including control keysEnter must be a separate argument, not \n in the string. Use -l for literal text so prompt content is never interpreted as key names.
capture-paneReads a pane's current screen or scrollback without disturbing the process-p prints to stdout; -S -200 reaches back into scrollback; -J joins wrapped lines. Without -S you only get the visible screen.
pipe-paneMirrors everything a pane emits to a command, continuously-O also captures existing output. This is your append-only audit log and it is one line.
wait-forBlocks until a named channel is signalled from anywhereTurns polling loops into instant callbacks: the agent signals -S name on completion, the waiter wakes immediately.
display -p '#{...}'Queries any format variable: pane cwd, current command, active flag, titleThe cheapest way to ask "is this pane running an agent, and is the user looking at it".

The orchestrator loop

  orchestrator (bash script, Makefile, or a parent agent)
        │
        │ 1  tmux new-window -d -n w1 -c "$WORKTREE"
        │ 2  tmux send-keys -t w1 'pi' Enter
        │ 3  tmux send-keys -t w1 -l "$PROMPT"      ← literal
        │    tmux send-keys -t w1 Enter             ← separate
        ▼
   ┌──────────────┐   pipe-pane -O 'cat >> logs/w1.log'
   │  worker w1   │ ─────────────────────────────────► audit log
   └──────┬───────┘
          │
          ├─ POLL   (works everywhere, wasteful, laggy)
          │    capture-pane -p -t w1 -S -5 | grep -q '❯' && done
          │
          └─ EVENT  (preferred: agent extension fires on completion)
               agent hook:  tmux wait-for -S w1-done
        ▲
        │ 4  tmux wait-for w1-done      ← blocks, zero CPU, no lag
        │ 5  read the transcript file the agent wrote, not the pane
        └─────────────────────────────────────────────────────────
Fig 10. Poll only when the agent gives you nothing better. Event signalling via wait-for or a Unix socket removes both the latency and the fragile prompt-glyph matching — and reading a transcript file the agent wrote beats scraping TUI chrome out of a pane.
fanout.shdispatch N agents, wait for all
#!/usr/bin/env bash
set -euo pipefail
SESSION="fanout"; LOGS="$PWD/.agent-logs"; mkdir -p "$LOGS"
tmux has-session -t "$SESSION" 2>/dev/null || tmux new-session -d -s "$SESSION"

dispatch() {                       # dispatch <name> <dir> <prompt>
  local n=$1 dir=$2 prompt=$3
  tmux new-window -d -t "$SESSION" -n "$n" -c "$dir"
  tmux pipe-pane -O -t "$SESSION:$n" "cat >> $LOGS/$n.log"
  tmux send-keys -t "$SESSION:$n" 'pi' Enter
  sleep 1                          # let the TUI take the terminal
  tmux send-keys -t "$SESSION:$n" -l "$prompt"
  tmux send-keys -t "$SESSION:$n" Enter
}

dispatch auth  .worktrees/auth  "Add refresh-token rotation. Commit when done."
dispatch tests .worktrees/tests "Fix the three flaky tests in spec/api. Commit."
dispatch docs  .worktrees/docs  "Update README for the new CLI flags. Commit."

# each agent's extension runs: tmux wait-for -S "$AGENT-done"
for n in auth tests docs; do
  tmux wait-for "$n-done" && echo "✓ $n finished"
done
tmux display-message -d 8000 "all agents finished — review diffs"

Giving an agent tmux access

You can go further and let the agent itself drive tmux — read another pane, start a dev server, interrupt a hung process. There are two ways, and the simpler one is usually correct.

ApproachWhen it winsCost
Plain bash + a convention in AGENTS.mdAlmost always. Agents already know tmux subcommands; they just need to know your pane addresses and what is off-limits. Zero install, works with every agent.You write the guardrails as prose, which the model may ignore
A tmux MCP server (several exist, in Python, Node and Rust)When you want typed tools, structured output, and enforced policy: read-only vs mutating vs destructive tiers, pane allowlists, command filters, and refusal to kill the agent's own paneAnother server to run and trust; only for MCP-capable agents (Pi ships no MCP by default)
Four rules before you hand over the keys

1. Never let an agent send-keys into a pane running another coding agent — you will get two models typing over each other, and a prompt injection channel between them.
2. Deny kill-server and kill-session outright. Good MCP servers detect the agent's own pane and refuse self-destructive calls; a prose rule is weaker but better than nothing.
3. capture-pane output is a credential leak. Anything printed in any pane — tokens, connection strings, env dumps — becomes model context the moment the agent reads it.
4. Treat anything an agent reads from another pane, or receives from another agent, as untrusted input rather than an instruction. A message from a peer can propose work; it cannot authorise it.

Cross-agent messaging without a framework

Two agents with different context — one near a production-shaped database, one in a dev checkout — is a more useful pattern than ten agents on one repo. tmux is enough transport for it: one pane reads another's output, or both talk through a tiny local broker with tokens, TTLs and acks. Published designs for exactly this converge on a few rules worth stealing: give every message a correlation ID, expire stale mail so a restarted agent never acts on a cancelled task, put redaction on the sender side, and reject any message that asks a peer to run a shell command.

┌─07Per-agent playbooks

The three terminal agents in the current race have genuinely different architectures, and each rewards a different tmux shape. Using the same layout for all three leaves value on the table.

opencode — the client/server split changes the topology

opencode is not one process. Running opencode starts a server and a TUI client that talks to it. That architectural fact is the most under-used tmux lever available, because it means the durable thing and the visible thing can live in different places.

 conventional (fine)          server/client split (better under tmux)
 ┌────────────────┐           ┌──────────────────────────────────────┐
 │ window 2       │           │ window 0  ── opencode serve --port   │
 │  opencode      │           │              4096   (never touched)  │
 │  (TUI+server)  │           ├──────────────────────────────────────┤
 └────────────────┘           │ window 2  ── opencode attach         │
                              │              http://localhost:4096   │
 kill the pane and you        ├──────────────────────────────────────┤
 kill the session             │ window 3  ── opencode run --attach   │
                              │              ... "one-shot task"     │
                              └──────────────────────────────────────┘
                              client panes are disposable; the server,
                              its MCP connections and warm state persist
Fig 12. With serve + attach, you can close and reopen the TUI freely, drive the same server from scripts with run --attach (skipping MCP cold-start on every invocation), and reach it from another machine. Set OPENCODE_SERVER_PASSWORD the moment the hostname is not localhost.
  • Subagent panes. Community plugins hook session.created for child sessions and auto-split a tmux pane running opencode attach <server> --session <id>, then close it when the child finishes. This requires starting opencode with an explicit --port so the plugin can construct the server URL — the single most common reason these integrations silently do nothing.
  • Session browsing. A tmux plugin can read opencode's local session database and give you a prefix + O popup that lists sessions by directory, status and age, then resumes one in a window. Child sessions fold into their parent so an orchestrator run reads as one row.
  • Layout. main-vertical with the main pane at ~60% is the reported sweet spot: agent large on one side, spawned children stacked on the other.
  • Gotchas. Leader is Ctrl+X, so it rarely collides with tmux. Escape latency and WSL2 clipboard are the two setup complaints that recur; both are fixed in Section 02.

Pi — designed on the assumption that you have tmux

Pi is unusual: it deliberately ships without subagents, background bash, plan mode, todos or MCP, and its documentation names tmux as the answer for two of those. This is not a gap, it is a design position — the harness stays small and you compose it with the tools you already run.

Pi omitsDocumented substitute
Sub-agentsSpawn Pi instances via tmux, or install an extension that does it your way
Background bashtmux. Full observability, direct interaction, no hidden process
Plan modeWrite plans to files
Built-in todosA TODO.md — the docs argue built-in todo state confuses models
Permission popupsRun in a container, or build a confirmation flow as an extension

The consequence is a small but sophisticated ecosystem of Pi extensions that treat tmux as the runtime. The patterns worth knowing:

  • Side agents. /agent <task> spawns a child Pi in its own tmux window and git worktree; the parent's status line lists which children are waiting; you switch windows to steer one; "LGTM" merges and tears everything down. The framing is deliberate — children are single-use and die with their topic branch, rather than long-lived role-based agents messaging each other.
  • Instant completion signalling. A Pi extension fires on agent_end, writes a clean transcript to a file, and signals a Unix socket or a tmux channel. A wait.sh blocks on that channel and returns the moment the child finishes — no polling, no scraping TUI chrome, and the parent reads the transcript file rather than the pane.
  • Supervision. Extensions exist that turn the current session into a supervisor which spawns a worker Pi in another pane and enforces process rules (for example, hand off before context exceeds a threshold).
  • Keys. Set extended-keys-format csi-u or Shift+Enter will submit instead of inserting a newline. Pi requests extended key reporting automatically when the Kitty keyboard protocol is unavailable.

Claude Code — agent teams put tmux in the product

Claude Code's experimental agent teams feature spawns each teammate as a separate Claude Code session. Its split-pane display mode is implemented on tmux (or iTerm2), which makes tmux a supported backend rather than a workaround.

  • Enable with CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1. The default display mode is in-process (it changed from auto in v2.1.179), so an upgrade can silently stop opening panes — set teammateMode explicitly to "auto" or "tmux" in ~/.claude/settings.json.
  • Split panes are not supported in VS Code's integrated terminal, Windows Terminal, or Ghostty. On macOS the docs suggest tmux -CC inside iTerm2 as the entry point — but note the conflict flagged in Section 02 if you also use Claude Code's fullscreen renderer.
  • Team config, including each teammate's tmux pane ID, lives under ~/.claude/teams/{team}/config.json. It is machine-managed state; do not hand-edit it.
  • Start with 3–5 teammates, 5–6 tasks each, and never two teammates on the same file. Token cost scales linearly with teammate count while speedup does not.
  • If a lead exits badly, teammate tmux sessions can be orphaned. tmux ls, then tmux kill-session -t <name> on the leftovers.
  • Quality gates: TeammateIdle, TaskCreated and TaskCompleted hooks can exit with code 2 to reject the transition and send feedback — a teammate about to go idle can be pushed back to work.
A note on which tool "wins"

You do not have to pick. Because every one of these is a process in a pty, a single tmux session can run opencode in window 2, Pi in window 3 and Claude Code in window 4 against three worktrees of the same repo. Several published setups do exactly that, and the multiplexer is the only reason it is boring rather than an integration project.

┌─08Remote, detached, and from your phone

The original tmux use case turns out to be the highest-leverage agent workflow: put the agents on a box that never sleeps, and treat every device you own as a viewport.

~/.ssh/config + shellattach-or-create
# one command, from any machine, always lands in the same place
ssh box -t 'tmux new-session -A -s main'

# -A = attach if it exists, create if it doesn't. This single flag
# removes every "did I already start a session" decision.

# flaky network (hotspot, train, café)? mosh instead of ssh:
mosh box -- tmux new-session -A -s main
# mosh is UDP with state sync; ssh is TCP and suffers on jitter.
# open UDP 60000-61000 on the firewall.

# make it the default login experience
# ~/.bashrc on the server:
[ -z "$TMUX" ] && [ -n "$SSH_TTY" ] && exec tmux new-session -A -s "$USER"

Why this matters more than it used to

An agent run is a long-lived, network-independent process that periodically needs a human decision. That is precisely the workload SSH plus tmux was built for. The published pattern is consistent across everyone doing it seriously: a cheap VPS, one named session per user, agents in windows, notifications pushed to a phone, and a reattach from whatever device is nearby when something needs a decision.

Fig 13. Multi-client attach is why detach-on-destroy off and aggressive-resize on matter: without them, one client closing a window or having a smaller screen degrades the session for everyone else.
The trade you are making

Unattended remote agents almost always means disabling permission prompts. Even people who do this routinely constrain it: limit no-approval runs to tasks where hostile instructions cannot plausibly enter the context, and move the blast radius into a container. A persistent session with permissions off, reachable from a phone, running against a repo with production credentials in .env is not a workflow — it is an incident waiting for a trigger.

tmux-specific hygiene

  • Scrollback is a secret store. With history-limit 100000, anything ever printed in a pane — a token, a connection string, an accidental env — is retrievable by anything that can call capture-pane, including an agent you gave tmux access to.
  • pipe-pane logs are evidence and liability. They are the best audit trail you can get for one line of config, and they write plaintext agent output to disk. Put them somewhere you would put logs, not in the repo, and rotate them.
  • synchronize-panes is a loaded gun. It broadcasts every keystroke to every pane in the window. Genuinely useful for kicking off the same setup prompt across three agents; catastrophic when you forget it is on. Bind it to a key with a visible status-bar indicator so the state is never ambiguous.
  • Cross-pane reads are an injection channel. Content an agent reads from another pane — issue text, a web page rendered in a browser TUI, another agent's output — is untrusted input. Anything downstream that can act on it needs a policy that is not "the model will notice".
  • Prefer OS sandboxes over containers for the inner loop. Agents fire hundreds of sub-millisecond shell calls per session; per-command container start-up is a non-starter, which is why the major agents ship Seatbelt/bubblewrap-style process sandboxes instead. Reach for containers or microVMs at the session boundary, not the tool-call boundary.

┌─13When not to use tmux

The interesting question in 2026 is not tmux versus nothing. It is tmux versus the agent-aware multiplexers that grew up around it.

OptionWhat it isChoose it when
tmuxThe substrate. Server-side persistence, remote attach, a 20-year-stable scripting API, the largest plugin ecosystem, and no awareness of agents whatsoever.You SSH anywhere, you script your workflow, or you want one thing that hosts every agent CLI including ones that don't exist yet
tmux + agent pluginsSidebars, status-bar monitors, state indicators, session browsers, worktree runners — layered on top, reading via capture-pane and hooks without interfering.Almost everyone running more than two agents. This is the default recommendation.

(cmux, Herdr, and others)		Rewrites that make per-pane agent state a first-class concept, with programmatic APIs over a local socket so an orchestrating agent can spawn panes, inject prompts and block on completion.Local, single-machine, many-agent work where state awareness matters more than ecosystem — and you accept a young tool. The argument against all of this

A recurring and honest position in community discussion: pane-hopping is a transitional interface. If orchestration matures, you will type into one panel where a coordinating agent lives and it will handle the rest — no more switching between windows to babysit workers. That is a plausible future, and it is not this year. The hedge is cheap: everything in this document is composed from generic primitives, so if a better interface arrives, you lose configuration, not a workflow.

The counter-argument is equally worth taking seriously — the more autonomous the agents get, the more valuable the ability to watch them becomes. Visibility and interruptibility are exactly what tmux sells.
