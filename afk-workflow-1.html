Verdict

Yes — but the tickets are not the unit of autonomy.

The implement phase can run fully AFK. What cannot run AFK is pointing agents at tickets and walking away, because the toolchain leaves three gaps that stall the loop within minutes. Each gap is documented by the tools' own authors. Each has a small, boring fix.

The working shape is a scheduler that owns all state and workers that own no state. Workers get a worktree, a ticket reference, and one job: leave a commit on a branch. Everything else — claiming, closing, unblocking, merging, escalating — belongs to a single coordinating process. Build that and the pipeline runs unattended; skip it and you get a board full of implemented-but-open tickets and a frontier that never advances.

  • /implement has no completion step

    It ends at the commit. It never closes the ticket and never ticks the acceptance criteria — confirmed on GitHub Issues and on the local markdown tracker, so this is not a tracker-integration bug. Since to-tickets defines the frontier as tickets whose blockers are closed, nothing closes, so nothing unblocks. The swarm implements wave one and then idles forever.

  • Parallel /implement in one checkout corrupts git

    The skills' own docs cite a field report: a git commit --amend in one session landing on another session's commit, a stash vanishing from refs/stash, commits on the wrong branch — one afternoon, three issues. Sessions share one working directory, one index, one HEAD. Worktrees fix two of those three; refs/stash is shared across worktrees, so the AFK prompt must also forbid git stash.

  • The in-run code review usually reviews nothing

    /implement runs /code-review before committing. code-review diffs <fixed-point>...HEAD, which excludes staged and working-tree changes. Unless an interim commit exists, that diff is empty. Run review as a separate pass, after the commit, against the branch point.

  • Bonus trap: the spec issue is labelled ready-for-agent too

    to-spec applies the label to the parent spec, which is an input designation rather than a work order. A poller cannot see that distinction and will try to build the entire feature in one run. This is the single most-reported rough edge on the skill. Strip the label after to-tickets, or exclude the spec number in the frontier query.

Fig. 01

The shape of the machine

Read it left to right. Tickets sit on the tracker under blocking edges. The frontier is the gate: open, unblocked, unclaimed. Past the gate, work fans onto isolated tracks — one git worktree each, no shared index. It all funnels back through one interlock, because merging is the one operation that must never happen twice at once.

02 · Contract

Where the skills stop

The main flow is a genuine pipeline — grill-with-docs → to-spec → to-tickets → implement → code-review — and its author is explicit that the order is the point. Steps one to three belong in one unbroken context window, because the grilling, the spec and the ticket split all build on the same thinking. Then each implement starts fresh.

What matters for automation is the seam after to-tickets. The skill produces an artifact and stops. Its own documentation says so plainly: there is no auto-dispatch mode, dispatch is manual, and "running it — one session at a time, or a fleet — is your job, not the skill's." That is the cliff your orchestrator is built on.

Two upstream conditions that decide whether AFK works

These are not orchestration concerns, but they are where the failure risk actually concentrates. An AFK fleet amplifies whatever quality the tickets already had.

  • Seams must be named in the spec. tdd refuses to write a test at an unconfirmed seam, and nothing inside implement agrees them. If the agreement happens nowhere, the precondition never fires and the run quietly becomes "just write the code" — with tests that pass and mean nothing.
  • Acceptance criteria must be falsifiable at the base commit. Three failure shapes recur: a criterion already true before any work, a criterion only another ticket can satisfy, and one that restates the request rather than deriving from the artifact. For each criterion, name the observation that would show it false, and confirm it fails at the commit the worker starts from. A vertical slice is red at base by construction — a horizontal one often isn't.
  • Pass full ticket references. /implement #2 resolves #2 against whatever numbered list the agent can see — a todo file, a checklist, another work list. The resolution is confident rather than fail-closed, so the mistake surfaces only after it has started building the wrong thing. Use owner/repo#42 and make the worker echo the title back before it begins.
  • Budget 100–150k tokens per ticket. Exploration, a red-green loop per seam, a full suite, a review. A non-trivial ticket exceeding 100k tokens is normal. If one keeps blowing out, the lever is upstream — split the ticket, don't raise the effort level.
03 · Breaks

Three ways the naive loop dies

Each panel below is a real, reported failure mode with a documented cause. They are worth drawing because they look like flaky agents when you hit them, and they are not — they are deterministic consequences of how the tools are built.

04 · Design

Scheduler owns state. Workers own nothing.

The single design decision that makes this tractable: workers never touch the tracker. They do not claim, do not comment, do not close. A worker receives a worktree path and a ticket body, and its contract is one line — leave a commit on this branch, or exit non-zero. Every state transition happens in one process that runs alone.

This collapses the hard distributed-systems problem into a local one. There is no claim race because there is one claimer. There is no lost update because there is one writer. You can add real distributed claiming later (§06) but you almost certainly won't need it.

05 · Frontier

Continuous frontier, not waves

The obvious scheduling model is Kahn's algorithm: topologically sort the DAG into waves, run each wave in parallel, barrier between them. Several existing pi orchestrators do exactly this. It is the wrong choice here, and the reason is ticket-size variance.

Tickets are sized to "one fresh context window", which in practice spans 20 minutes to 90 minutes. A wave barrier idles every finished worker until the slowest member of the wave lands. With the variance these tickets actually have, that is a large fraction of your throughput given away for a scheduling convenience you don't need.

Poll the frontier instead. Every time any ticket closes, recompute open ∧ unblocked ∧ unclaimed and fill any free slot immediately. A ticket becomes eligible the instant its last blocker closes, not at the next barrier. The implementation is simpler than Kahn's — you never materialise the wave structure at all, you just ask the tracker a question on a timer.

Getting the frontier from the tracker

GitHub issue dependencies went generally available in August 2025 with full REST and webhook support, which is what makes this cheap. The issue_dependencies_summary.blocked_by count reflects open blockers only, so it is a live gate you can read directly rather than a graph you have to reconstruct. And because to-tickets publishes blockers first, their numbers always exist at creation time — gh issue create --blocked-by 12,15 works.

frontier query · GitHubbash
# open, labelled ready, unassigned, and with zero open blockers
gh issue list --state open --label ready-for-agent \
  --json number,title,assignees \
  --jq '.[] | select(.assignees | length == 0) | .number' \
| while read n; do
    blocked=$(gh api "repos/$REPO/issues/$n" \
      --jq '.issue_dependencies_summary.blocked_by // 0')
    [ "$blocked" -eq 0 ] && [ "$n" != "$SPEC_ISSUE" ] && echo "$n"
  done
Do not skip the spec exclusion

Without [ "$n" != "$SPEC_ISSUE" ] your first worker picks up the parent spec — which carries ready-for-agent because to-spec put it there — and attempts to build the entire feature in a single run. It will burn your whole budget and produce an unmergeable branch. Strip the label from the spec after to-tickets, exclude it by number, or both.

06 · Claiming

Three tiers of atomicity — pick the cheapest that fits

"Two agents could claim the same ticket" is the concern that makes people over-engineer. It only exists if more than one process claims. Tier 1 removes the concurrency instead of managing it, and is what you should ship.

07 · State

The state machine the skills don't ship

The canonical vocabulary is five triage labels: needs-triage, needs-info, ready-for-agent, ready-for-human, wontfix. That set was designed for humans triaging inbound issues, and it has two documented gaps that bite an AFK runner specifically.

First, there is no blocked state — an issue that is fully specified but waiting on another issue is "technically ready-for-agent" and misleading, so an agent picks it up and hits a wall. Second, and worse for automation, there is no terminal awaiting-verification state, without which an AFK runner can re-queue finished tickets. Both are acknowledged as real and neither has shipped.

So add your own, namespaced so they never collide with the canonical five. Only the scheduler writes them.

08 · Isolation

Worktrees, and the one thing they don't isolate

A git worktree gives each worker its own working directory, its own index, and its own HEAD. That kills two of the three corruption modes in Fig. 03B. It does not give each worker its own refs/stash — the stash reflog lives in the shared common directory, so a stash pushed in one worktree is visible and poppable in another. That is the third failure, and worktrees alone do not fix it.

Two mitigations, use both. Forbid git stash in the worker's appended system prompt, and give each worker a clean tree it never needs to stash from in the first place.

Enforcing the guardrails properly

Prompt text is a request, not a constraint. pi's tool_call extension event fires before the tool executes and can return { block: true, reason } — with terminate: true to stop the batch without another model call. Twenty lines of TypeScript loaded with -e ./guard.ts turns the list above from a hope into a rule. Worth doing once you are running unattended overnight rather than watching.

09 · Merge

One track through the junction

Merging is the only stage that must be strictly serial. Two branches that each pass their gate in isolation can still break the build together — that is the entire reason merge queues exist. The integrator takes a lock, rebases one branch onto the current integration tip, runs the gate after the rebase, and only then fast-forwards.

Rebase rather than merge, so the integration branch stays linear and each ticket lands as a reviewable unit. Gate after rebase, not before, because the worker's green was measured against a stale base.

10 · Ladder

Every ticket must terminate

"Fully autonomous" does not mean every ticket lands. It means the loop never blocks on you. A ticket that cannot be built must reach a terminal state and get out of the way, so the rest of the graph keeps moving.

The subtle failure here is worth calling out because it cost real money during testing. If escalation is expressed only as a remote label change, and that write fails — rate limit, permissions, network — the ticket returns to the frontier and is dispatched again immediately. The run below did that 49 times in 60 seconds before the ledger fix. Loop termination must be recorded locally and authoritatively. The remote label is for humans; the local marker is for the loop.

swarm.sh — the scheduler

The tracker adapter is five functions at the top. Everything below them is tracker-agnostic; swapping GitHub Issues for .scratch/ markdown means rewriting those five and nothing else.

swarm.shchmod +x · run from repo root
#!/usr/bin/env bash
# swarm.sh — autonomous ticket execution for pi + mattpocock/skills
#
#   The scheduler. Owns every write to the tracker. Workers own nothing.
#
#   Usage:  ./swarm.sh            run until the frontier is empty
#           ./swarm.sh --dry-run  print the frontier and exit
#           ./swarm.sh --status   show ledger state and exit
#
#   Requires: git >= 2.30, gh (authenticated), pi >= 0.84, jq, flock, timeout
set -euo pipefail

# ─────────────────────────────────────────────────────── configuration ──
REPO="${SWARM_REPO:-$(gh repo view --json nameWithOwner -q .nameWithOwner)}"
SPEC_ISSUE="${SWARM_SPEC_ISSUE:-0}"      # parent spec — MUST be excluded
INTEGRATION="${SWARM_INTEGRATION:-integration}"
MAX_PARALLEL="${SWARM_MAX_PARALLEL:-3}"
WORKER_TIMEOUT="${SWARM_WORKER_TIMEOUT:-45m}"
POLL_SECONDS="${SWARM_POLL:-20}"
MAX_ATTEMPTS="${SWARM_MAX_ATTEMPTS:-2}"
MODEL="${SWARM_MODEL:-sonnet}"
REVIEW_MODEL="${SWARM_REVIEW_MODEL:-$MODEL}"
GATE="${SWARM_GATE:-npm run typecheck && npm test}"

ROOT="$(git rev-parse --show-toplevel)"
SWARM="$ROOT/.swarm"
WT="$ROOT/.wt"
mkdir -p "$SWARM"/{result,attempts,pid,done} "$SWARM/logs" "$WT"
export PI_CACHE_RETENTION=long

log() { printf '%s  %s\n' "$(date +%H:%M:%S)" "$*" >&2; }

# ───────────────────────────────────────────── tracker adapter · GitHub ──
# Swap these five functions to move to Linear, Jira, or local markdown.
# Nothing else in this file knows what a tracker is.

tracker_frontier() {
  # open ∧ ready-for-agent ∧ unassigned ∧ zero open blockers ∧ not the spec
  gh issue list --repo "$REPO" --state open --label ready-for-agent \
      --limit 200 --json number,assignees \
      --jq '.[] | select(.assignees | length == 0) | .number' \
  | while read -r n; do
      [ "$n" = "$SPEC_ISSUE" ] && continue
      local_blocked=$(gh api "repos/$REPO/issues/$n" \
        --jq '.issue_dependencies_summary.blocked_by // 0' 2>/dev/null || echo 0)
      [ "$local_blocked" -eq 0 ] && echo "$n"
    done
}

tracker_claim() {           # returns 0 only if we actually won the claim
  local n=$1 me
  me=$(gh api user --jq .login)
  gh issue edit "$n" --repo "$REPO" --add-assignee "@me" \
     --add-label "swarm:claimed" >/dev/null 2>&1 || return 1
  # readback — --add-assignee is last-write-wins, not compare-and-swap
  gh issue view "$n" --repo "$REPO" --json assignees \
     --jq ".assignees[].login" | grep -qx "$me"
}

tracker_release() {
  local n=$1
  gh issue edit "$n" --repo "$REPO" --remove-assignee "@me" \
     --remove-label "swarm:claimed" --remove-label "swarm:building" \
     --remove-label "swarm:in-review" >/dev/null 2>&1 || true
}

tracker_label() {           # tracker_label <n> <add> [remove]
  local n=$1 add=$2 rm=${3:-}
  if [ -n "$rm" ]; then
    gh issue edit "$n" --repo "$REPO" --add-label "$add" --remove-label "$rm" >/dev/null 2>&1 || true
  else
    gh issue edit "$n" --repo "$REPO" --add-label "$add" >/dev/null 2>&1 || true
  fi
}

tracker_close() {
  local n=$1 sha=$2
  # tick the acceptance criteria implement never touches
  local body
  body=$(gh issue view "$n" --repo "$REPO" --json body -q .body \
         | sed 's/^- \[ \]/- [x]/')
  gh issue edit "$n" --repo "$REPO" --body "$body" \
     --remove-label "swarm:in-review" --remove-label "ready-for-agent" >/dev/null 2>&1 || true
  gh issue close "$n" --repo "$REPO" \
     --comment "Merged into \`$INTEGRATION\` as \`$sha\` by swarm." >/dev/null
}

tracker_escalate() {
  local n=$1 reason=$2 log=$3
  gh issue comment "$n" --repo "$REPO" --body \
"**Swarm gave up after $MAX_ATTEMPTS attempts.**

Reason: $reason

Branch \`ticket/$n\` is pushed. Worktree kept at \`.wt/$n\`.
Last 60 lines of the run log:

\`\`\`
$(tail -n 60 "$log" 2>/dev/null || echo '(no log)')
\`\`\`" >/dev/null 2>&1 || true
  gh issue edit "$n" --repo "$REPO" --add-label "ready-for-human" \
     --remove-label "ready-for-agent" >/dev/null 2>&1 || true
  tracker_release "$n"
}

# ─────────────────────────────────────────────────────────────── ledger ──
# A ticket is terminal when it has merged or been escalated. This marker is
# LOCAL and authoritative for loop control: never let termination depend on a
# remote label write succeeding, or a failed write re-queues the ticket forever.
terminal()      { [ -f "$SWARM/done/$1" ]; }
mark_terminal() { touch "$SWARM/done/$1"; }
attempts()      { cat "$SWARM/attempts/$1" 2>/dev/null || echo 0; }
bump_attempt()  { echo $(( $(attempts "$1") + 1 )) > "$SWARM/attempts/$1"; }
running_count() { find "$SWARM/pid" -type f 2>/dev/null | wc -l | tr -d ' '; }
is_running()    { [ -f "$SWARM/pid/$1" ] && kill -0 "$(cat "$SWARM/pid/$1")" 2>/dev/null; }

# ─────────────────────────────────────────────────────────────── worker ──
WORKER_RULES='HARD RULES FOR THIS SESSION — violating any of them corrupts sibling agents:
- NEVER run `git stash`. The stash reflog is shared across all worktrees.
- NEVER run `git commit --amend`, `git rebase`, `git merge`, or `git push`.
- NEVER run `git checkout <branch>` or `git switch`. Stay on the current branch.
- NEVER touch the issue tracker. Do not run `gh issue` for any reason.
- Allowed git: add, commit, diff, log, status, show.
You are in a dedicated git worktree on a dedicated branch. Your entire job is to
leave one or more commits on this branch. Something else merges and closes.'

run_worker() {
  local n=$1
  local dir="$WT/$n" branch="ticket/$n"
  local logf="$SWARM/logs/$n.jsonl"
  local base; base=$(git rev-parse "$INTEGRATION")

  git worktree remove --force "$dir" >/dev/null 2>&1 || true
  git branch -D "$branch" >/dev/null 2>&1 || true
  git worktree add -b "$branch" "$dir" "$INTEGRATION" >/dev/null 2>&1

  (
    cd "$dir"
    # ── build ──────────────────────────────────────────────────────────
    timeout --kill-after=60s "$WORKER_TIMEOUT" \
      pi -p --approve --mode json --model "$MODEL" \
         --exclude-tools ask_question \
         --append-system-prompt "$WORKER_RULES" \
         "/skill:implement $REPO#$n

Read the ticket with: gh issue view $n --repo $REPO
Echo its title back before you start, then build exactly that ticket and nothing else.
Commit to the current branch when the acceptance criteria are met." \
      >> "$logf" 2>&1 || { echo "failed:implement" > "$SWARM/result/$n"; exit 0; }

    # a run that produced no commit is a failure regardless of exit code
    if [ "$(git rev-list --count "$base..HEAD")" -eq 0 ]; then
      echo "failed:no-commit" > "$SWARM/result/$n"; exit 0
    fi

    # ── review, fresh context, read-only, after the commit ─────────────
    timeout --kill-after=60s 20m \
      pi -p --approve --model "$REVIEW_MODEL" \
         --tools read,grep,find,ls \
         "/skill:code-review $base

The originating ticket is $REPO#$n.
End your response with exactly one line: VERDICT: PASS or VERDICT: FAIL" \
      > "$SWARM/logs/$n.review.md" 2>&1 || true

    if grep -q '^VERDICT: FAIL' "$SWARM/logs/$n.review.md"; then
      echo "failed:review" > "$SWARM/result/$n"; exit 0
    fi

    # ── merge, strictly serialized ─────────────────────────────────────
    if flock -w 3600 "$SWARM/merge.lock" \
         "$ROOT/integrate.sh" "$n" "$branch" "$INTEGRATION" >> "$logf" 2>&1; then
      echo "merged:$(git -C "$ROOT" rev-parse --short "$INTEGRATION")" > "$SWARM/result/$n"
    else
      echo "failed:merge" > "$SWARM/result/$n"
    fi
  ) &

  echo $! > "$SWARM/pid/$n"
  log "→ #$n dispatched (attempt $(attempts "$n"), pid $!)"
}

# ─────────────────────────────────────────────────────────────── reaper ──
reap() {
  local f n result kind
  for f in "$SWARM"/pid/*; do
    [ -e "$f" ] || continue
    n=$(basename "$f")
    is_running "$n" && continue
    rm -f "$f"

    result=$(cat "$SWARM/result/$n" 2>/dev/null || echo "failed:vanished")
    rm -f "$SWARM/result/$n"
    kind=${result%%:*}

    if [ "$kind" = "merged" ]; then
      mark_terminal "$n"
      tracker_close "$n" "${result#merged:}"
      git worktree remove --force "$WT/$n" 2>/dev/null || true
      log "✓ #$n merged and closed — children may now be unblocked"
    else
      bump_attempt "$n"
      if [ "$(attempts "$n")" -gt "$MAX_ATTEMPTS" ]; then
        mark_terminal "$n"
        git -C "$WT/$n" push -u origin "ticket/$n" >/dev/null 2>&1 || true
        tracker_escalate "$n" "${result#*:}" "$SWARM/logs/$n.jsonl"
        log "✗ #$n escalated to ready-for-human (${result#*:})"
      else
        tracker_label "$n" "ready-for-agent" "swarm:claimed"
        tracker_release "$n"
        git worktree remove --force "$WT/$n" 2>/dev/null || true
        log "↻ #$n requeued (${result#*:}), attempt $(attempts "$n")/$MAX_ATTEMPTS"
      fi
    fi
  done
}

# ───────────────────────────────────────────────────────────── main loop ──
case "${1:-}" in
  --dry-run) log "frontier:"; tracker_frontier; exit 0 ;;
  --status)  log "running: $(running_count)/$MAX_PARALLEL"
             for f in "$SWARM"/attempts/*; do [ -e "$f" ] && \
               echo "  #$(basename "$f") attempts=$(cat "$f")"; done; exit 0 ;;
esac

git rev-parse --verify "$INTEGRATION" >/dev/null 2>&1 \
  || git branch "$INTEGRATION" HEAD
log "swarm start · repo=$REPO · integration=$INTEGRATION · slots=$MAX_PARALLEL"

idle_polls=0
while true; do
  reap

  free=$(( MAX_PARALLEL - $(running_count) ))
  dispatched=0
  if [ "$free" -gt 0 ]; then
    while read -r n; do
      [ "$free" -le 0 ] && break
      is_running "$n" && continue
      terminal "$n" && continue
      if tracker_claim "$n"; then
        tracker_label "$n" "swarm:building" "swarm:claimed"
        run_worker "$n"
        free=$(( free - 1 )); dispatched=$(( dispatched + 1 ))
      else
        log "· #$n claimed by someone else, skipping"
      fi
    done < <(tracker_frontier)
  fi

  if [ "$(running_count)" -eq 0 ] && [ "$dispatched" -eq 0 ]; then
    idle_polls=$(( idle_polls + 1 ))
    if [ "$idle_polls" -ge 2 ]; then
      log "frontier empty and nothing running — done"
      exit 0
    fi
  else
    idle_polls=0
  fi

  sleep "$POLL_SECONDS"
done

integrate.sh — the junction

Called only under flock. Uses a dedicated merge worktree so the primary checkout is never disturbed, and finishes with git update-ref passing the expected old value — a compare-and-swap that fails loudly if anything moved the integration tip while the lock was supposedly held.

integrate.shnever call directly — always via flock
#!/usr/bin/env bash
# integrate.sh — the single-track junction.
#
#   Called ONLY under flock, by exactly one process at a time:
#     flock -w 3600 .swarm/merge.lock ./integrate.sh <ticket> <branch> <integration>
#
#   Rebases the ticket branch onto the current integration tip, resolves any
#   conflict with an agent, re-runs the gate against the merged result, and
#   fast-forwards. Exits non-zero if the work cannot land — the caller retries
#   or escalates.
set -euo pipefail

N="$1"; BRANCH="$2"; INTEGRATION="$3"
ROOT="$(git rev-parse --show-toplevel)"
GATE="${SWARM_GATE:-npm run typecheck && npm test}"
MERGE_DIR="$ROOT/.wt/merge"

log() { printf '  [merge #%s] %s\n' "$N" "$*" >&2; }

# A dedicated merge worktree so we never disturb the primary checkout,
# and so an agent resolving conflicts has somewhere legitimate to work.
git worktree remove --force "$MERGE_DIR" 2>/dev/null || true
git worktree add --detach "$MERGE_DIR" "$BRANCH" >/dev/null 2>&1
cd "$MERGE_DIR"

cleanup() { cd "$ROOT"; git worktree remove --force "$MERGE_DIR" 2>/dev/null || true; }
trap cleanup EXIT

log "rebasing $BRANCH onto $INTEGRATION"
if ! git rebase "$INTEGRATION" >/dev/null 2>&1; then
  log "conflict — handing to resolving-merge-conflicts"

  # The skill's own rule: always resolve, never --abort. It reads commit
  # messages and originating tickets for both sides to recover intent.
  timeout --kill-after=60s 25m \
    pi -p --approve --exclude-tools ask_question \
       --append-system-prompt 'You are resolving a rebase conflict inside a dedicated
merge worktree. Do not run git stash, git push, or gh issue. You may run
git add, git rebase --continue, git status, git diff, git log.' \
       "/skill:resolving-merge-conflicts

Rebasing branch $BRANCH onto $INTEGRATION for ticket #$N.
Preserve both intents. Never run git rebase --abort.
Finish the rebase completely, then stop." >&2 || true

  if [ -d "$(git rev-parse --git-path rebase-merge)" ] || \
     [ -d "$(git rev-parse --git-path rebase-apply)" ]; then
    log "rebase still in progress after resolution attempt — abandoning"
    git rebase --abort >/dev/null 2>&1 || true
    exit 1
  fi
  log "conflict resolved"
fi

# Gate AFTER the rebase. The worker's green was measured against a stale base;
# two branches that each pass alone can still fail together.
log "running gate against the rebased result"
if ! bash -c "$GATE" >&2; then
  log "gate red after rebase — not landing"
  exit 1
fi

# Fast-forward only. If this is not a fast-forward, something raced us and the
# lock was not held — fail loudly rather than creating a merge commit.
cd "$ROOT"
if ! git update-ref "refs/heads/$INTEGRATION" \
      "$(git -C "$MERGE_DIR" rev-parse HEAD)" \
      "$(git rev-parse "$INTEGRATION")"; then
  log "integration tip moved under the lock — aborting"
  exit 1
fi

log "landed as $(git rev-parse --short "$INTEGRATION")"
exit 0

guard.ts — optional, but do it before you sleep through a run

Prompt text is a request. pi's tool_call event fires before the tool executes and can return { block: true, reason }, which makes the worker rules actually binding. Load with -e ./guard.ts.

guard.tspi -e ./guard.ts
/**
 * guard.ts — turns the worker guardrails from a prompt request into a rule.
 *
 *   pi -e ./guard.ts -p --approve "/skill:implement owner/repo#42"
 *
 * A worker runs inside a shared git common directory. `refs/stash` is shared
 * across every worktree, and history rewrites break the integrator's rebase.
 * Prompt text is a request; `tool_call` blocking is a constraint.
 *
 * Returning { block: true } stops the tool before it executes. `terminate: true`
 * ends the agent early when every finalized result in the batch is terminating,
 * which avoids paying for a follow-up model call just to be told no.
 */
import { isToolCallEventType, type ExtensionAPI } from "@earendil-works/pi-coding-agent";

/** Each rule: a matcher against the raw command, and why it is refused. */
const FORBIDDEN: Array<{ test: RegExp; why: string }> = [
  {
    test: /\bgit\s+stash\b/,
    why: "refs/stash is shared across all worktrees — stashing here can be popped by a sibling agent onto the wrong branch.",
  },
  {
    test: /\bgit\s+commit\b[^\n|;&]*--amend/,
    why: "amending rewrites a commit the integrator may already be rebasing.",
  },
  {
    test: /\bgit\s+(rebase|merge|cherry-pick|reset\s+--hard)\b/,
    why: "history and integration belong to the integrator, not the worker.",
  },
  {
    test: /\bgit\s+push\b/,
    why: "the worker never publishes; the scheduler owns the remote.",
  },
  {
    // Allows `git checkout -- <path>` and `git checkout -p` (discarding local
    // changes is legitimate). Blocks anything that moves or creates a branch.
    test: /\bgit\s+(checkout|switch)\b(?!\s+(--(\s|$)|-p\b))/,
    why: "stay on the branch you were given; switching corrupts the ticket↔branch mapping.",
  },
  {
    test: /\bgh\s+(issue|pr)\b/,
    why: "the tracker has exactly one writer, and it is the scheduler.",
  },
  {
    test: /\bgit\s+worktree\b/,
    why: "worktree lifecycle is the scheduler's; creating one here leaks state.",
  },
];

export default function (pi: ExtensionAPI) {
  pi.on("tool_call", (event) => {
    if (!isToolCallEventType("bash", event)) return;

    const command = event.input.command;
    for (const rule of FORBIDDEN) {
      if (rule.test.test(command)) {
        return {
          block: true,
          reason:
            `Blocked by swarm guard: ${rule.why}\n` +
            `Finish your work with add/commit only, and leave the branch as-is.`,
          terminate: false, // let the model recover and choose another path
        };
      }
    }
  });
}

The local-markdown adapter

If you configured to-tickets for local files rather than GitHub, tickets are one file per ticket at .scratch/<feature>/issues/<NN>-<slug>.md with a Blocked by: line and a Status: line. Substitute these five:

tracker adapter · local markdowndrop-in replacement
ISSUES=".scratch/$FEATURE/issues"

tracker_frontier() {
  for f in "$ISSUES"/*.md; do
    n=$(basename "$f" | cut -d- -f1)
    grep -q '^Status: *ready-for-agent' "$f" || continue
    blocked=0
    for b in $(sed -n 's/^Blocked by: *//p' "$f" | tr ',' ' '); do
      [[ "$b" =~ ^[0-9]+$ ]] || continue
      grep -q '^Status: *resolved' "$ISSUES/$b"-*.md 2>/dev/null || blocked=1
    done
    [ "$blocked" -eq 0 ] && echo "$n"
  done
}
# Claim is a file write, so flock the whole read-pick-claim (Tier 2, Fig. 06)
tracker_claim()  { sed -i 's/^Status: .*/Status: claimed/' "$ISSUES/$1"-*.md; }
tracker_release(){ sed -i 's/^Status: .*/Status: ready-for-agent/' "$ISSUES/$1"-*.md; }
tracker_close()  { sed -i -e 's/^Status: .*/Status: resolved/' -e 's/^- \[ \]/- [x]/' "$ISSUES/$1"-*.md; }
tracker_escalate(){ sed -i 's/^Status: .*/Status: ready-for-human/' "$ISSUES/$1"-*.md; }
One caveat on local mode

The tickets live inside the repo, so every worker's worktree contains a copy of the ticket files, and the integrator will happily try to merge status-line edits between branches. Keep .scratch/ out of the worktrees — either write ticket state to a path outside the repo, or add .scratch/ to .git/info/exclude and manage it only from the primary checkout. GitHub Issues avoids this class of problem entirely, which is the main argument for using it.

The bug this caught

First run of the failure scenario: 49 dispatches in 60 seconds. Escalation set the remote label but tracker_release cleared the assignee, so the ticket re-entered the frontier and was picked up again immediately — forever. With a live model that is a runaway spend with no natural stopping point.

The fix is the .swarm/done/<n> marker and the terminal "$n" && continue guard in the dispatch loop. Loop control is local and authoritative; the remote label is a human-facing projection. 13 · Runbook

Going from tickets to an unattended run

The ordering matters here, so the numbers are real. Steps 1–3 are once per repo; 4–7 are once per feature.

  1. Install the skills where trust can't hide them

    Global install sidesteps pi's project-trust gate entirely, which removes a whole class of silent failure in fresh worktrees.

    npx skills@latest add mattpocock/skills -a pi -g
# then, in the repo, once:
pi "/skill:setup-matt-pocock-skills"

  2. Create the swarm labels

    Namespaced so they never collide with the canonical five.

    for l in claimed building in-review; do
  gh label create "swarm:$l" --color BFA43A --force
done

  3. Define the gate and prove it green

    The gate is the only objective signal the machine has. If it is flaky, the swarm will requeue good work and escalate it. Run it ten times on a clean tree first.

    export SWARM_GATE="npm run typecheck && npm test -- --run"

  4. Run the human phases in one unbroken window

    Grill, spec, tickets — no clearing, no compaction between them. Name the TDD seams in the spec and check every acceptance criterion actually fails at the base commit. This is where AFK quality is decided.

  5. Neutralise the spec issue

    Non-negotiable. Otherwise your first worker tries to build the whole feature.

    gh issue edit 40 --remove-label ready-for-agent
export SWARM_SPEC_ISSUE=40   # belt and braces

  6. Dry run, then one ticket, then the swarm

    Confirm the frontier is what you expect before spending anything. Then run a single ticket with one slot and read the whole log by hand — you are validating the ticket quality, not the script.

    ./swarm.sh --dry-run
SWARM_MAX_PARALLEL=1 ./swarm.sh
SWARM_MAX_PARALLEL=3 ./swarm.sh

  7. Watch the first parallel wave, then leave

    Concurrency of 3 is the sweet spot for most repos: each pi session is a full process, and memory plus provider rate limits bite before CPU does. Raise it only after you have seen a clean wave.

    tail -f .swarm/logs/*.jsonl | jq -rc 'select(.type=="tool_execution_start") | .toolName'

Build or adopt?

Adopt if you want the mature parts — journaled resume, cost accounting, a TUI. Build if you want to understand the thing that runs unattended against your repo overnight. The scripts here are ~250 lines precisely so that when the swarm stalls, the answer is in a file you wrote rather than in someone else's abstraction. Whichever you choose, check it for the terminal-ledger property from §12 before trusting it with a budget.

15 · Limits

What this does not solve

Being straight about the boundaries, because the failure modes that remain are the ones that will actually cost you.

  • Ticket quality is the ceiling, and it is set by a human. The swarm faithfully builds whatever to-tickets produced. A horizontally-sliced ticket gets built as a horizontal slice. Over-decomposition — twelve tickets for a three-line change — is the most reported friction on that skill, and an AFK fleet will dutifully spin up twelve worktrees for it.
  • Semantic conflicts pass every check here. Two branches that each typecheck, each pass tests, and merge without a textual conflict can still be jointly wrong. The post-rebase gate catches the subset your tests cover. Nothing catches the rest, and no amount of orchestration will.
  • An agent reviewing agent-written code is a weak signal. Running review in a fresh read-only session with no memory of writing the code is meaningfully better than the in-run review, which is why the design does it — but it is still a model grading a model. Treat VERDICT: PASS as a smoke test, not an approval.
  • The wide-refactor tail stays serial. Expand → migrate batches → contract is a dependency chain by construction. Only the migrate batches parallelise. That is the graph's shape and no scheduler fixes it.
  • No published measurement exists. The claim that grilling saves rework is plausible and, so far, unmeasured — nobody has published a controlled comparison against going straight to code. The same is true of parallel-agent throughput numbers circulating for pi worktree swarms. Treat the productivity claims, including the shape of Fig. 05, as reasoned estimates rather than data.
  • pi has no permission system. It runs with the privileges of whoever launched it, and you are now launching it unattended, in a loop, with a model choosing the commands. If that matters for your repo, containerise before you automate — pi documents three patterns for it.
The honest summary

The orchestration problem is small and solvable — about 250 lines, and this report's diagrams describe all of it. The hard part was never parallelism or merging. It is that implement stops at a commit and the frontier is defined by closure, so the whole loop hinges on a state transition that no skill performs. Own that transition and the rest follows.
